## 오늘의 지도: 세 곳에 적힌 같은 값과, 그것을 맞추는 두 방향

week1의 지도는 명령의 흐름, week2는 리소스 사이의 참조, week3은 state 파일이 사는 곳, week4는 값이 어디에 적혀 있는지, week5는 코드가 어느 폴더에 있는지였습니다. 오늘의 지도는 **같은 값이 세 곳에 적혀 있다는 것**과, 그 셋이 어긋났을 때 화살표가 어느 방향으로 움직이는지입니다.

### ① 세 곳: 코드 · state · 실물

```
    코드                       state                        실물
    practice/main.tf           S3 의 week06/app/            AWS 계정의 버킷
                               terraform.tfstate

    Env = "study"              "Env": "study"               Env : study

    내가 직접 씁니다            apply 가 씁니다               apply 가 만듭니다
    git 에 올라갑니다           S3 에 올라갑니다              콘솔에서 눈으로 봅니다
    terraform plan 이          terraform state show 가      AWS 콘솔이
    읽습니다                    읽습니다                      보여줍니다

    셋이 같으면 plan 이 No changes 라고 말합니다.
```

### ② Block A: 콘솔이 나중에 끼어듭니다

```
 1) apply 직후                 코드 study  =  state study  =  실물 study
                                                                  │
 2) 콘솔에서 Env 를 HACKED 로                                       │ 사람이 손댐
                              코드 study  =  state study  ≠  실물 HACKED
                                                     ^
                                             state 는 아직 옛날 값입니다.
                                             terraform state show 로 확인합니다. (A-4)

 3) terraform plan            refresh 가 실물을 물어보고 화면에 차이를 보여줍니다
                              Plan: 0 to add, 1 to change, 0 to destroy.     (A-5)

 4) 여기서 길이 둘로 갈립니다.                                       (A-6)

    terraform apply -refresh-only        terraform apply
      state 만 실물에 맞춥니다              실물을 코드에 맞춥니다
      실물은 그대로 HACKED                  실물이 study 로 돌아옵니다
      코드는 그대로 study                   셋이 다시 같아집니다
      -> plan 은 여전히 1 to change
```

### ③ Block B: 콘솔이 먼저 만들어 놓습니다

```
 1) 콘솔에서 버킷 생성          코드 없음    state 없음    실물 있음 (버전 관리 ON)
                                                            ^
                                            Terraform 은 존재 자체를 모릅니다.
                                            plan 에 나오지 않습니다.        (B-1)

 2) 코드에 빈 블록만            코드 있음    state 없음    실물 있음
                              plan 은 "새로 만들겠다"고 합니다. 여기서 apply 하면 안 됩니다.

 3) terraform import           코드 있음    state 있음    실물 있음         (B-2)
                              import 는 state 만 채웁니다. 코드는 안 채웁니다.

 4) terraform plan             No changes.                                (B-3)
                              그런데 버전 관리는 코드 어디에도 없습니다.
                              plan 은 코드에 적힌 것만 비교합니다.

 5) 부속 리소스 블록 2개 추가   plan: 2 to add. 실물에 이미 있는데도 그렇습니다.  (B-4)
 6) 각각 import                plan: No changes. state list 4줄            (B-5)
```

### ④ 두 명령이 미는 방향

```
                    apply 는 이쪽으로 밀어냅니다
        코드 ───────────────────────────────────> 실물
          ^                                        │
          │                                        │
          │        state                           │
          │          ^                             │
          │          └─────────────────────────────┘
          │            refresh 는 이쪽으로 끌어옵니다
          │            (apply -refresh-only 가 state 에 적어둡니다)
          │
          └── 코드를 고치는 것은 사람뿐입니다.
              import 도 terraform 도 .tf 파일을 대신 써주지 않습니다.
```

세 번째 줄이 오늘 겪을 불편의 자리입니다. state 는 명령으로 채워지는데 코드는 사람이 씁니다.

| 스텝 | 지도에서 하는 일 |

### [실습] A-2. TODO ①: week3 버킷을 이어 쓰고 값 채우기 (3분)

지금 하는 일은 오늘 만들 것의 state 를 week3 버킷의 새 `key` 에 두는 것입니다.

```bash
# pwd == practice
cd practice
cp example.tfvars terraform.tfvars
```

`terraform.tfvars`를 열어 `project_name` 을 본인 값으로 바꿉니다. `region` 은 그대로 둡니다.

```hcl
region       = "ap-northeast-2"
project_name = "boaz26-w6-kdh1834"
```

> [!WARNING]
> `project_name` 은 그대로 S3 버킷 이름이 됩니다. **버킷 이름은 AWS 계정 안이 아니라 전 세계에서 유일해야 합니다.** 다른 사람이 이미 쓰고 있는 이름이면 만들 때 실패합니다. 본인 github id 를 꼭 넣으세요.
>
> 소문자 · 숫자 · 하이픈만 쓸 수 있습니다. 대문자나 밑줄을 넣으면 `variables.tf` 의 검사에 걸립니다.
>
> ```
> Error: Invalid value for variable
>
>   on terraform.tfvars line 1:
>    1: project_name = "BOAZ26-W6-KDH1834"
>     ├────────────────
>     │ var.project_name is "BOAZ26-W6-KDH1834"
>
> S3 버킷 이름 규칙입니다. 소문자 · 숫자 · 하이픈만 쓸 수 있습니다.
> ```

이제 `backend.tf`를 열어 `CHANGE-ME` 두 곳을 **week3 값**으로 바꿉니다. 방금 정한 `project_name`과 다른 값입니다.

```hcl
terraform {
  backend "s3" {
    bucket         = "boaz26-w3-kdh1834-tfstate"
    key            = "week06/app/terraform.tfstate"
    region         = "ap-northeast-2"
    dynamodb_table = "boaz26-w3-kdh1834-tflock"
    encrypt        = true
  }
}
```

> [!WARNING]
> `key`는 이미 채워져 있습니다. 건드리지 마세요. week5 코드에서 복사해 오면 `key`가 `week05/prod/terraform.tfstate`로 나옵니다. 그 줄까지 붙여넣으면 지난주 state 를 인수해서 VPC 와 EC2 가 삭제 대상이 됩니다.

`terraform.tfvars`는 커밋하지 마세요. `.gitignore` 가 막고 있지만 확인은 본인이 합니다.

### [실습] A-3. TODO ②: 드리프트 실습용 버킷 만들기 (4분)

지금 하는 일은 코드 · state · 실물 셋이 모두 같은 상태를 만드는 것입니다. 여기서부터 어긋내기 시작합니다.

`practice/main.tf`를 열어 TODO ② 자리에 리소스 하나를 적습니다.

```hcl
resource "aws_s3_bucket" "drift_demo" {
  bucket = "${var.project_name}-drift"

  tags = {
    Name  = "${var.project_name}-drift"
    Study = "boaz-terraform-26"
    Env   = "study"
  }
}
```

`Env` 태그가 오늘의 실험 대상입니다. 태그는 무과금 속성이라 콘솔에서 바꿔도 요금이 달라지지 않습니다. 개념워크북 6번.

```bash
# pwd == practice
terraform init
terraform plan
```

```
Plan: 1 to add, 0 to change, 0 to destroy.
```

지금 하는 일은 드리프트를 감지하고, `plan` 출력에서 과거형과 미래형을 구분하는 것입니다.

### [실습] [관찰 ✍️] A-6. 두 길을 모두 걸어봅니다 (3분)

```bash
terraform state show aws_s3_bucket.drift_demo   # HACKED 로 바뀜

terraform plan                          # No changes.

# Block B : 콘솔이 먼저 만들어 놓습니다
#   콘솔에서 {project_name}-manual 버킷 생성 (버전 관리 Enable)

terraform plan                          # Plan: 1 to add  <- apply 하지 말 것

terraform plan                          # No changes.  <- 그런데 버전 관리는 코드에 없습니다

terraform plan                          # Plan: 2 to add  <- apply 하지 말 것
terraform import aws_s3_bucket_versioning.manual         <버킷명>

terraform state list | tee ~/week6-state-list.txt        # 4줄

terraform fmt && terraform validate && terraform output

# Block C : 정리
terraform plan -destroy                 # 4 to destroy
```

## 부록. 트러블슈팅

| 증상 | 원인 | 해결 |
|------|------|------|
| `resource address "..." does not exist in the configuration` | 코드에 블록을 안 적고 import 함 | 먼저 `resource` 블록을 적으세요. B-2 |
| `Resource already managed by Terraform` | 같은 주소로 중복 import | `terraform state list` 로 확인. 필요하면 `state rm` 후 재시도. B-2 |
| import 가 "없는 것"이라며 실패 | 버킷 이름 오타 또는 리전 불일치 | 콘솔 리전이 서울인지, 이름이 정확한지 확인. `aws s3api head-bucket --bucket <이름>` |
| import 후에도 diff 가 남음 | 코드에 속성이 다 안 채워짐 | `terraform state show <주소>` 로 실물을 보고 하나씩 옮겨 적기. B-4 |
| `plan` 이 `No changes` 인데 콘솔 설정이 코드에 없음 | 그 설정이 코드에 없어서 비교 대상이 아님 | 부속 리소스 블록을 적고 각각 import. B-3 · B-4 |
| `state show` 와 콘솔 값이 다름 | state 는 자동으로 갱신되지 않음 | 정상입니다. `plan` 이나 `apply -refresh-only` 가 refresh 합니다. A-4 |
| `-refresh-only` 후에도 `plan` 이 `1 to change` | 코드가 그대로라서 | 정상입니다. 코드를 고치거나 `apply` 하세요. A-6 |
| S3 버킷 이름이 이미 쓰인다는 오류 | 버킷 이름은 전 세계에서 유일 | `project_name` 에 본인 github id 를 넣고 뒤에 숫자를 붙이기 |
| `Invalid value for variable` | `project_name` 에 대문자나 밑줄 | 소문자 · 숫자 · 하이픈만. A-2 |
| `Reference to undeclared resource` | output 이 아직 없는 리소스를 가리킴 | TODO 순서대로 진행. B-6 |
| `destroy` 가 `BucketNotEmpty` 로 실패 | 버킷에 객체가 있음 | `aws s3 rm s3://<버킷> --recursive` 후 재시도. C-1 |
| `Failed to get existing workspaces: S3 bucket ... does not exist` | week3 버킷 이름 오타 또는 bootstrap 없음 | A-1로 돌아가기 |
| `Error acquiring the state lock` | 동시 실행 또는 비정상 종료 | 아무도 작업 안 하는 것 확인 후 `terraform force-unlock <LOCK_ID>` |
| `Warning: Deprecated Parameter` | `dynamodb_table` 사용 | 정상입니다. week3 개념워크북 9번 |
| `zsh: no matches found` | 주소의 대괄호를 셸이 해석 | 작은따옴표로 감싸기. B-7 |
| `plan` 숫자가 표와 전혀 다름 | `backend.tf` 의 `key` 가 지난 주 것 | apply 하지 말고 `key` 를 `week06/app/...` 로. A-2 |

> 이 문서에 실린 오류 메시지 네 종류(`resource address ... does not exist in the configuration` · `Resource already managed by Terraform` · `Reference to undeclared resource` · `Invalid value for variable`)와 `terraform state list` · `terraform state show` 의 출력 모양은 `solution/` 코드를 Terraform 1.15.8 · `darwin_arm64` 에서 실제로 실행해 얻은 값입니다. AWS 자격증명 없이 재현되므로 과금이 없습니다.
>
> 세 리소스의 import ID 가 모두 버킷 이름이라는 것은 AWS provider 문서(`aws_s3_bucket` · `aws_s3_bucket_versioning` · `aws_s3_bucket_public_access_block`)의 Import 절에서 확인했습니다. `aws_s3_bucket` 을 `bucket` 한 줄만 적고 import 했을 때 버전 관리가 diff 로 잡히지 않는 것과 태그는 diff 로 잡히는 것은 provider 스키마를 직접 조회해 확인했습니다. 버킷 리소스의 `versioning` 블록은 `Optional` 이면서 `Computed` 라 코드에 없으면 state 값을 그대로 두고, `tags` 는 `Computed` 가 아니라서 코드에 없으면 비우려 합니다.
>
> 이 문서가 인용한 Terraform 안내 문구는 같은 버전 바이너리의 메시지 목록에서 원문을 대조했습니다. `Note: Objects have changed outside of Terraform` 과 그 아래 설명문, `has changed` · `will be updated in-place` · `forces replacement`, `No changes. Your infrastructure matches the configuration.`, `Import successful!` 과 `... will henceforth be managed by Terraform.`, A-6 의 `-refresh-only` 승인 프롬프트 두 줄, 평소 `apply` 의 `Do you want to perform these actions?`, `Destroy complete! Resources:` 가 여기에 해당합니다. 문구는 원문이고, 그 문구가 실제로 이 실습에서 뜨는지는 apply 로 확인하지 않았습니다.
>
> 확인하지 않은 것은 숫자와 값입니다. `plan` 마지막 줄의 `1 to add` · `1 to change` · `2 to add`, `state list` 4줄, `4 destroyed` 는 리소스 정의에서 센 값입니다. 태그 diff 에 찍히는 값, `terraform output` 의 값 모양, `aws s3 ls` 출력도 실제로 실행해 얻은 것이 아닙니다. 비용은 개념워크북 Part 6과 같습니다.
